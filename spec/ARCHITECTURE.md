### 1.2 נימוקים לבחירות

-   **Next.js לעומת React עם Backend נפרד או Astro:** Next.js מאפשר לנהל
    את שלושת המסכים ואת נקודת ה־API באותו Repository ובאותו פרויקט. כך
    נמנעים משני שירותים נפרדים וממורכבות Deployment מיותרת. React לבדו
    היה מחייב בחירה ותפעול של Backend נוסף; Astro אפשרי, אך אינו מספק
    יתרון משמעותי למוצר האינטראקטיבי הקטן הזה.
-   **Vercel לעומת Netlify או Cloudflare Workers:** Vercel מספקת מסלול
    ישיר ל־Next.js, חיבור ל־GitHub ו־Preview Deployments. Netlify
    ו־Cloudflare הן חלופות ראויות, אך אינן מצדיקות שינוי ב־Stack עבור
    מוצר זה.
-   **OpenAI SDK לעומת קריאת `fetch` ישירה:** ה־SDK הרשמי מפשט את העבודה
    מול ה־API ומספק ממשק TypeScript מוכר. קריאת `fetch` ישירה אפשרית, אך
    תחייב יותר טיפול ידני.
-   **Structured Outputs לעומת טקסט חופשי:** פלט התואם Schema מפחית
    שגיאות מבניות ומקל לוודא שיש בדיוק ארבע אפשרויות ותשובה נכונה אחת.
    יש לאמת תמיכה של המודל שנבחר לפני השימוש.
-   **ללא Database:** אין משתמשים, היסטוריה או ניקוד מתמשך. מצב המשחק
    והניקוד יישמרו בזיכרון של ממשק המשתמש בלבד וייעלמו בטעינה מחדש או
    בסגירת הסשן.
-   **PWA מינימלי:** נדרש לאפשר התקנה, אך אין צורך ב־Push Notifications,
    סנכרון, או יכולת לייצר שאלות Offline. ה־Service Worker יטפל רק
    במעטפת הסטטית, אם נדרשת שמירה בסיסית של משאבי האפליקציה.

### 1.3 הערה חשובה על GPT-5

בתיעוד הרשמי של OpenAI, דף המודל `GPT-5` מסומן כ־**Deprecated** בעת
ביצוע המחקר. לכן ה־PRD מאפשר שימוש ב־GPT-5 **או במודל חדש יותר של
OpenAI שאושר על ידי בעל המוצר**. `OPENAI_MODEL` יהיה משתנה תצורה. לפני
חיבור ה־API יש להציג לבעל המוצר המלצה על מודל (מהיר, זול ונתמך), לקבל את
אישורו ולבדוק שהמודל זמין לחשבון. אין להחליף את המודל בשקט. מאחר שמסך
הטעינה מבטיח „רק כמה שניות", יש להעדיף מודל או הגדרה עם זמן תגובה קצר.

### 1.4 עלויות ומגבלות

-   **Vercel Hobby:** התוכנית החינמית מיועדת לשימוש אישי ולא מסחרי. לפי
    ה־PRD המוצר הוא פרויקט אישי / לימודי ללא מטרה מסחרית, ולכן תוכנית
    Hobby מתאימה. אם מטרת המוצר תשתנה, יש לבדוק מעבר לתוכנית מתאימה, כגון
    Pro. המכסות והתמחור עשויים להשתנות.
-   **OpenAI API:** חיוב ה־API נפרד ממנוי ChatGPT ומבוסס על המודל
    והשימוש. **כבר בתחילת הפיתוח (Milestone 2)** יש להגדיר בחשבון תקרת
    הוצאה קשיחה והתראות, ולצמצם את גודל הקלט והפלט. התקרה היא ההגנה
    העיקרית מפני שימוש חריג, מאחר שנקודת ה־API ציבורית. העלות בפועל תלויה
    במספר השאלות ובתעריף המודל.
-   **Vercel Functions:** הקריאה ל־AI ממתינה לתגובה חיצונית, ולכן יש
    להגדיר timeout סביר ולהחזיר הודעת שגיאה ידידותית אם הבקשה מתארכת.
    אין צורך ב־Background Jobs עבור פעולה קצרה זו.
-   **אין Supabase או שירות Database אחר:** הוספת מסד נתונים אינה מוצדקת
    לפי ה־PRD, ולכן לא מוגדרים פרויקטים נפרדים ל־Development
    ול־Production ב־Supabase ולא נדרשים Database Migrations.

## 2. ארכיטקטורת המערכת

### 2.1 מבט כללי

המערכת היא יישום Web מלא בפרויקט Next.js יחיד. ממשק המשתמש נשלח לדפדפן,
אך בקשות ל־OpenAI מתבצעות רק ב־Backend. מפתח ה־API אינו נשלח לדפדפן.

``` mermaid
flowchart TD
    U["ילד / דפדפן או PWA"] --> FE["Next.js Frontend"]
    FE -->|POST /api/trivia| API["Next.js Route Handler"]
    API --> VALID["בדיקת קלט ומגבלות"]
    VALID --> SAFE["סינון נושא ותוכן"]
    SAFE -->|מתאים| AI["OpenAI API: GPT-5"]
    SAFE -->|לא מתאים| REJECT["תשובת נושא לא מתאים"]
    AI --> CHECK["בדיקת פלט ותקינות"]
    CHECK -->|תקין| API
    CHECK -->|לא תקין / כשל| ERR["טיפול בשגיאה"]
    API --> FE
    REJECT --> FE
    ERR --> FE
    GH["GitHub Repository"] -->|Push / Merge| V["Vercel Build ו־Deployment"]
    V --> FE
    V --> API
```

### 2.2 רכיבי המערכת ואחריותם

#### Frontend

אחראי על:

-   הצגת שלושת המסכים: בית, שאלות טריוויה ואודות.
-   הצגת תיבת הנושא, כפתור בקשת שאלה, השאלה וארבע אפשרויות התשובה.
-   ניהול מצב המשחק הנוכחי: הנושא, השאלה, האם כבר נבחרה תשובה, המשוב
    והניקוד המצטבר.
-   מניעת בחירה שנייה באותה שאלה באמצעות נעילת אפשרויות התשובה לאחר
    הבחירה הראשונה.
-   עדכון הניקוד בנקודה אחת בלבד לאחר תשובה נכונה.
-   הצגת התשובה הנכונה לאחר תשובה שגויה.
-   הצגת מצבי טעינה, נושא לא מתאים ושגיאה.
-   שליחת בקשות ל־Backend בלי לכלול מפתח OpenAI בקוד צד־לקוח.

#### Backend --- `POST /api/trivia`

אחראי על:

-   קבלת הנושא מהדפדפן ובדיקת תקינותו.
-   טיפול בנושא ריק כבקשה לשאלה כללית.
-   הגבלת אורך הקלט והגנה מפני בקשות חריגות.
-   בדיקת התאמת הנושא לילדים.
-   יצירת הנחיות קבועות למודל בעברית ובשפה המתאימה לגילאי 9--12.
-   קריאה ל־OpenAI API באמצעות משתנה סביבה סודי.
-   בדיקת התגובה לפני החזרתה ללקוח.
-   החזרת תגובה מובנית או שגיאה כללית שאינה חושפת מפתחות, Stack Traces
    או פרטי ספק מיותרים.

#### OpenAI API

אחראי לייצר תוכן לפי ההנחיות. אין להעביר למודל מידע אישי של ילד; הבקשה
כוללת רק את הנושא שהוזן ואת ההנחיות הנדרשות ליצירת השאלה.

#### Vercel

אחראית ל־Hosting של Next.js, להפעלת Route Handler, ל־HTTPS, לניהול משתני
הסביבה של Production ולפריסות אוטומטיות מ־GitHub.

#### GitHub

משמש לניהול קוד המקור, תיעוד והיסטוריית שינויים. לא נשמרים בו סודות,
מפתחות API או קובצי `.env` המכילים ערכים סודיים.

### 2.3 חלוקה ל־Modules ושכבות לוגיות

יש לשמור על הפרדה לוגית גם כאשר כל הקוד נמצא באותו Repository:

1.  **UI / Pages** --- המסכים, רכיבי הממשק והניווט.
2.  **Game State** --- מצב השאלה הנוכחית, בחירת התשובה והניקוד בזיכרון
    הדפדפן.
3.  **API Client** --- פונקציה בצד־לקוח ששולחת בקשה ל־`/api/trivia`
    וממירה תגובות לשגיאות ידידותיות.
4.  **API Route** --- שכבת HTTP לבדיקת בקשה, הפעלת השירות והחזרת תשובה.
5.  **Trivia Service** --- כללי היישום: טיפול בנושא ריק, הנחיות לילדים,
    בדיקת התאמה ובדיקת הפלט.
6.  **OpenAI Adapter** --- מודול יחיד שמשתמש ב־SDK הרשמי, קורא את
    `OPENAI_MODEL` ומטפל בשגיאות של ספק ה־AI.

אין צורך ב־Microservices, Message Queue, Cache חיצוני או שכבת Repository
ל־Database, מאחר שאין מסד נתונים.

## 3. Data Model ואחסון

### 3.1 אין Database

אין ישויות מתמידות ואין צורך ב־Database או ב־File Storage. המידע נשמר רק
בזיכרון בזמן השימוש.

### 3.2 מבנה הנתונים של שאלה

ה־Backend יחזיר אובייקט לוגי במבנה הבא:

``` json
{
  "question": "איזה כוכב לכת מכונה הכוכב האדום?",
  "options": [
    "נוגה",
    "מאדים",
    "צדק",
    "שבתאי"
  ],
  "correctOptionIndex": 1
}
```

דרישות למבנה:

-   `question`: מחרוזת בעברית.
-   `options`: מערך של ארבע מחרוזות לא ריקות.
-   `correctOptionIndex`: מספר שלם בטווח 0--3.
-   אין להחזיר שאלה אם המודל סירב, אם הפלט חסר, או אם המבנה אינו תקין.
-   יש לבדוק בצד השרת את מספר האפשרויות ואת תקינות האינדקס גם כאשר
    משתמשים ב־Structured Outputs.

### 3.3 מצב משחק בצד־לקוח

מצב המשחק בזיכרון כולל:

-   `currentTopic` --- הנושא הנוכחי, אם הוזן.
-   `currentQuestion` --- השאלה וארבע האפשרויות שהתקבלו.
-   `answered` --- האם המשתמש כבר בחר תשובה לשאלה הנוכחית.
-   `feedback` --- מצב המשוב: הצלחה או כישלון.
-   `score` --- מספר התשובות הנכונות בסשן הנוכחי.
-   `recentQuestions` --- טקסט השאלות האחרונות שנשאלו (עד 10), כדי לבקש
    מהמודל לא לחזור עליהן.

מצב המשחק נשמר ברמה שמשותפת לכל המסכים, כך שהוא נשמר במעבר בין בית,
שאלות ואודות. הניקוד והשאלות האחרונות מתאפסים בעת טעינה מחדש או פתיחת סשן חדש. אין לשמור אותו ב־Local
Storage, Cookies או Database, בהתאם לדרישה שלא לשמור מידע בין ביקורים.

## 4. APIs ואינטגרציות

### 4.1 נקודת API פנימית

`POST /api/trivia`

**בקשת JSON:**

``` json
{
  "topic": "חלל",
  "recentQuestions": ["איזה כוכב לכת מכונה הכוכב האדום?"]
}
```

אם `topic` חסר או ריק לאחר הסרת רווחים, יש להתייחס לבקשה כשאלה כללית.
אורך `topic` מוגבל ל־40 תווים. `recentQuestions` אופציונלי: מערך של עד 10
מחרוזות באורך מוגבל; ה־Backend מעביר אותן למודל כרשימת שאלות שאין לחזור
עליהן.

**תגובה מוצלחת --- `200 OK`:**

``` json
{
  "question": "איזה כוכב לכת מכונה הכוכב האדום?",
  "options": ["נוגה", "מאדים", "צדק", "שבתאי"],
  "correctOptionIndex": 1
}
```

**תגובה עבור נושא שאינו מתאים --- `422 Unprocessable Content`:**

``` json
{
  "error": {
    "code": "TOPIC_NOT_ALLOWED",
    "message": "הנושא הזה לא מתאים לחידון. נסו לבחור נושא אחר."
  }
}
```

**תגובה במקרה של כשל זמני --- `503 Service Unavailable`:**

``` json
{
  "error": {
    "code": "QUESTION_UNAVAILABLE",
    "message": "לא הצלחנו ליצור שאלה כרגע. נסו שוב."
  }
}
```

קודי HTTP והמבנים לעיל הם חוזה המימוש המומלץ ל־API הפנימי. ה־Frontend
מחליט מה להציג לפי `code` בלבד, והטקסטים שמוצגים למשתמש מוגדרים בממשק לפי
`DESIGN.md` (בלשון רבים). השדה `message` משמש לתיעוד ולגיבוי בלבד. פרטי
שגיאה פנימיים יישמרו בלוגים מצומצמים ולא יוחזרו ללקוח.

### 4.2 זרימת יצירת שאלה

1.  המשתמש מזין נושא ולוחץ על כפתור יצירת השאלה.
2.  ה־Frontend משבית זמנית את כפתור הבקשה ומציג מצב טעינה, כדי למנוע
    שליחת בקשות חוזרות בשוגג.
3.  ה־Frontend שולח `POST /api/trivia`.
4.  ה־Backend מאמת שהבקשה היא בפורמט תקין, שהנושא הוא מחרוזת ושאורכו
    עד 40 תווים, ושרשימת `recentQuestions` (אם קיימת) תקינה.
5.  אם הנושא ריק, הוא ממופה לבקשת טריוויה כללית.
6.  ה־Backend מפעיל בדיקת התאמה לפי כללי הבטיחות. ניתן להיעזר ב־OpenAI
    Moderation API, אך אין להסתמך עליו לבדו: יש לשלב הוראות מפורשות
    למודל ובדיקת הפלט לפני הצגתו.
7.  אם הנושא נדחה, ה־Backend מחזיר `TOPIC_NOT_ALLOWED` בלי לבקש מהמודל
    ליצור שאלה בנושא.
8.  אם הנושא מתקבל, ה־Backend שולח בקשה ל־OpenAI עם הנחיות: עברית בלבד,
    התאמה לגילאי 9--12, שאלה אחת, ארבע אפשרויות, תשובה נכונה אחת,
    עובדות מוכרות ויציבות, הימנעות מהשאלות שב־`recentQuestions`,
    והימנעות מתוכן שאינו מתאים לילדים. הנחיית הבטיחות הבסיסית הזו קיימת
    כבר מ־Milestone 2, עוד לפני שכבות הסינון המלאות (Milestone 4).
9.  יש להשתמש ב־Structured Outputs עם JSON Schema כאשר המודל הפעיל תומך
    בכך. ה־Backend בודק את התגובה בפועל ואינו מסתמך רק על הנחיות
    הפרומפט.
10. לאחר בדיקה מוצלחת, ה־Backend מערבב באקראי את סדר ארבע האפשרויות,
    מעדכן את `correctOptionIndex` בהתאם, ומחזיר את השאלה והאפשרויות
    ל־Frontend. כך התשובה הנכונה לא תופיע תמיד באותו מקום.
11. ה־Frontend מציג את השאלה. לאחר בחירת תשובה אחת, הוא נועל את אפשרויות
    התשובה ומציג משוב.
12. תשובה נכונה מוסיפה נקודה אחת בזיכרון הסשן; תשובה שגויה מציגה את
    התשובה הנכונה. בקשת השאלה הבאה יוצרת שאלה חדשה ואינה דורשת שמירת
    היסטוריה.

## החלטות מרכזיות (ADRs)

### ADR-1: עיצוב ב־CSS Modules ואייקונים כ־SVG ידני

**הקשר:** ה־Style Guide מגדיר שפה עיצובית מדויקת: צבעים, גדלים, אייקונים בעובי קו 1.9 עם וריאנט מלא ללשונית הפעילה, ואיורי נושאים שטוחים. ARCHITECTURE מאפשר CSS רגיל או CSS Modules, בלי ספריית UI גדולה.

**החלטה:** ה־Design tokens מוגדרים כ־CSS variables ב־`src/app/globals.css`, וכל רכיב מעוצב ב־CSS Module משלו. האייקונים (`src/components/icons.tsx`) ואיורי הנושאים (`src/components/TopicIllustrations.tsx`) נכתבים כ־SVG ידני, בלי ספריית אייקונים. הגופנים Rubik ו־Heebo נטענים דרך `next/font/google`.

**השלכות:** אין תלויות נוספות, והמראה תואם ל־Style Guide בדיוק. אייקון חדש מוסיפים ידנית ל־`icons.tsx`. צבעים שאין להם HEX ב־Style Guide (Grape Dark, Sunny Soft, Coral Soft, Sky Soft, Stone) נגזרו כגוונים של צבעי הבסיס ומוגדרים במקום אחד ב־`globals.css`.
